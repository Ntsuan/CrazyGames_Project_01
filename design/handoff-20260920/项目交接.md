## 4. 优先修复：合成品质文字仍会漏点

**优先级 P2；最近已复现版本 v2.37.1。交接读取的 v2.38 中仍可见同类实现。**

### 复现

1. 准备同部位、同品质的三个合成材料。
2. 手指按在按钮内“报废”“破损”等彩色品质文字上。
3. 按住跨过一次 renderPanels 刷新，然后在 10px 内松手。
4. 原品质 span 脱离文档，合成没有执行，tapBtn 残留。

本轮曾用 2×、100ms 短点、9px 位移复现；通过测试夹具把刷新时刻对齐到短点内部。不是只有长按才受影响。

按在 button 本身、图标或外层标题上的行为不能替代品质子节点的测试。elementFromPoint 已确认品质 span 可以成为实际命中目标。

### 原因及修改入口

在 `renderPanels()` 中搜索 `gs-fuset-`：外层结构虽然已常驻，但每次仍对标题设置 innerHTML，重新创建两个品质 span。v2.37.1 对应约第 1160 行；v2.38 读取时约第 1176 行，后续以函数和标识定位。

### 建议

- 将输入品质、产出品质 span 也固定创建，只更新其 class 和 textContent。
- 不要只缓存整段 HTML：品质在按住期间发生变化时，目标仍必须稳定。
- 按钮确需隐藏或目标失效时，主动清理对应手势，避免残留状态影响下次操作。
- 保留业务层合成材料、技能候选、升级费用的执行时校验。

### 验收

在 1×/2× 下分别点击空白、图标、普通标题、两个品质文字；叠加定时刷新、实际掉落、自动换装。每个有效手势恰好执行一次，取消手势不执行，tapBtn/tapId 和按压样式无残留。

证据：[v2.37.1 复验报告](/Users/zmy/WorkBuddy/CrazyGames/design/qa-input-speed-v2.37.1-20260920/修复状态复验.md)、[100ms 短点记录](/Users/zmy/WorkBuddy/CrazyGames/design/qa-input-speed-v2.37.1-20260920/quality-short-tap.json)。

## 5. 待收尾：在途切换倍速

**最近已复现版本 v2.37.1；CHANGELOG 已明确记为已知限制。**

以 1× 开始敌人跑入，100ms 后切换 2×：新 runCfg 已为 180ms，但当前 transition 仍为 0.36 秒，约 421ms 才结束，仍接近原 1× 的 360+50ms。

相关入口：`effSpeed()`、`runCfg()`、`sDur()`、`enemyRunIn()`、`openingRunIn()`、`startFloorTransit()`、`sceneSwap()`、`runIn()` 和 CSS 的 `--spd`。

建议统一管理阶段进度和剩余时间，切速时同步更新动画及完成回调。不要只缩放新建 setTimeout，也不要只改 CSS。继续保留 runSeq，避免复位或重塑后旧回调生效。

还需注意：

- 暂停战斗与暂停演出不是一回事。当前转场设置 paused=true，但演出仍需继续，不能把整个调度一起冻结。
- 背景切换仍有固定 480ms 等待；跑出淡出回调略早于位移完成，需统一核对阶段边界。
- 部分增益与无敌时间使用 Date.now。若迁入游戏时间，应记录行为变化并做数值回归。
- UI 刷新、触摸反馈、存档时间戳、日志实际耗时和外部交互保持真实时间。
- 既定规则仍是“只加速已通关楼层”，进入新楼层恢复 1×。

验收：跑入、死亡、换怪、跨层中途双向切速，无重播、跳位、动画结束后空等、重复刷怪或错误解暂停。同配置已通关楼层，排除人工选择等待后，2× 整体耗时应接近 1× 的一半。

## 6. v2.38 新增变化：待验证

相对 v2.37.1，交接时已看到：玩家 death 动画、spawnMob 清 death 状态、真实死亡等待动画结束后调用 showWallModal、超时受阻保持直接弹窗，以及死亡时清除复位确认状态的后续修改。

建议接手后的补测顺序：

1. 死亡素材存在、请求成功、8 帧序列和最后一帧正常，1×/2× 时长一致对应。
2. 普通死亡、超时受阻分别进入正确流程；死亡期间不继续攻击、结算或重复弹窗。
3. 射击动作中死亡时正确切换 death；重塑、复位、读档后清除死亡姿态。
4. 死亡动画期间点击复位、切换倍速、切后台或刷新，不产生旧回调覆盖新弹窗。
5. 死亡发生在复位确认期间后，重塑完成，再过技能层，三选一仍能正常出现。
6. VERSION、CHANGELOG、版本快照一致。

这些是待测场景，不是已确认的新增缺陷。旧测试若假设死亡瞬间就出现弹窗，应按新设计检查动画阶段与最终结果；不能简单把延迟导致的断言失败算作业务缺陷，也不能直接删掉原竞态覆盖。

## 8. 测试方式与注意事项

- 在独立 design/qa-* 目录冻结 index.html 和 assets，记录哈希；用独立 localhost 端口和存储，避免污染用户真实存档与 logs。
- 浏览器工具测试与 Node VM 逻辑测试分开报告。模拟 TouchEvent 能检查处理器，不能代替手机原生滚动、兼容 click 与事件目标行为。
- 固定状态、随机数、帧步长和演出时间再做数值比较；记录倍速是否处于可生效楼层。
- 现有 core-tests.cjs 有版本硬断言，复制到新 QA 目录后应更新 C40 的版本预期。不要因此把 73/74 直接理解为真实游戏缺陷，也不要将旧通过数当成最新版本验收。
- 旧 harness 使用 DOM 桩，不足以覆盖实际 DOM 替换、CSS 时长和浏览器命中区域，按钮问题必须补浏览器验证。
- 源码若仍被其他开发过程更新，先对齐测试快照；报告明确冻结版本和哈希。
- 截图在状态变化后至少等两个 requestAnimationFrame 再保存，避免取到旧画面。
- 测试结束关闭自己的服务和标签页，仅清理本次独立存储。
